# QuickExit v0.11.5 — Authentication Reliability & Security Verification

Local audit only; no browser account operations or hosted requests were performed.

## Audit and changes

The v0.11.2 observer retains the restoration lock until the explicit session lookup resolves. Null INITIAL_SESSION events never establish sign-out. Lookup errors retain uncertainty and the exact restoration-unavailable message. Successful null lookup and explicit SIGNED_OUT establish signed-out state. Intentional `demo=1` and disabled account access still select Demo explicitly. The hook locks before hydration, and account-dependent views hide balances while unresolved. Store initialization, import, dispatch, conflict resolution and background retries remain guarded. Account loading does not create a portfolio; the existing reviewed-choice confirmation remains required. The SDK browser client uses cookie-backed persistent sessions and browser token refresh; these settings were not weakened. Proxy verification does not redirect unresolved authentication to Demo; APIs verify identity independently.

Found and fixed: a delayed TOKEN_REFRESHED or USER_UPDATED for an older account could supersede a newer identity or undo logout. The observer now accepts those maintenance events only for the latest known identity. The latest identity is recorded before queued store updates, covering same-turn races. SIGNED_IN still permits deliberate account changes. Synchronous getSession throws now follow the same locked failure path as rejected lookups. No UI, routing, cookie settings, responsive styles, trading calculations or registration gates changed.

Added regressions: delayed maintenance events after account switch/logout, legitimate same-account refresh and later sign-in, synchronous lookup failure and recovery, and actual workspace-store restoration/remount with zero mock cloud commits. Existing tests cover null initialization, missing sessions, rejection, detach, queued races, logout, account isolation, initialization confirmation and error action locks.

Changed files: `src/lib/account/auth-session.ts`, `tests/auth-foundation.test.mjs`, `tests/cloud-workspace.test.mjs`, build version in `src/lib/build-info.ts` and `tests/secure-accounts.test.mjs`, this report, the prepared Account A procedure and the updated controlled-authentication checkpoint links. Prior v0.11.4 responsive work is preserved.

## Validation

181 tests passed, zero failures. TypeScript, lint and production build passed. Production verification explicitly disabled account access and registration. Tests use local fake authentication, transport and database fixtures; no genuine session restoration is proven by them.

## Remaining limits and next step

Whether Account A's existing private-browser context is reusable is unknown; the earlier owner-reported guest return is not proof that a new sign-in is required. Expiration, cookie/storage restrictions and hosted refresh behavior remain untested. A lookup that never settles stays safely locked but has no automatic timeout/retry. Auth events carry no application sequence number: the guard rejects old-account maintenance events and stale initial/queued results, but cannot distinguish a late SIGNED_IN from a deliberate new sign-in or an old SIGNED_OUT from a genuine provider sign-out. Server-side identity verification and account-scoped generation guards remain necessary and unchanged. getSession restores SDK state; cloud APIs independently verify the user. No new evidence establishes hosted JWT isolation, real two-device conflicts or immutable hosted receipts.
