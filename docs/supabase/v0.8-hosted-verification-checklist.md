# QuickExit v0.8 hosted Supabase verification checklist

This is a plan, not approval to execute hosted changes. Current public accounts and
registration stay disabled. All activity is simulated. Local auth fixtures and
PGlite checks passed; real Supabase authentication and synchronization are unverified.

## Permission boundaries

| Stage | Allowed activity | Approval needed before execution? |
| --- | --- | --- |
| Read-only review | Inspect dashboard settings; run the two catalog SELECT reports below; compare migration and build metadata | No hosted mutation involved |
| Test preparation | Change development auth/SMTP/redirect settings; create dedicated accounts; enable account flags in the development-connected local test app; send email | Yes, separate approval specifying project and scope |
| Hosted acceptance | Auth/session operations; simulated portfolio imports/trades/notes; replay/conflict tests; even expected-denied write attempts | Yes, dedicated A/B test records only |
| Production rollout | Push, deploy, change production settings or enable accounts/registration | Separate release approval; outside this checklist's test execution scope |
| Hosted rollback/cleanup | Restore hosted settings, revoke test sessions, delete test records or restore data | Separate explicit approval; never implied by a failing test |

## 1. First action — read-only project and configuration review

- [ ] In Supabase, open the intended **quickexit-dev** project. Verify its project
      reference and origin in General/API settings against the intended development
      project. Do not infer identity from display name alone. Do not use production.
- [ ] Record the checkpoint SHA, UTC test date, project label/reference and tester.
      Keep private evidence access-restricted. Never include keys, tokens, passwords,
      email links or user payloads in reports.
- [ ] View Authentication settings without clicking Save. Record whether Email is
      enabled, Confirm Email is on, Allow new users to sign up is off, and anonymous
      sign-ins are off. Unexpected signup enablement is a blocker; report it rather
      than changing it under read-only authorization.
- [ ] Inspect URL Configuration, email templates, SMTP delivery restrictions, session
      policy and rate limits. Record differences from the target settings in step 3.
      Do not reveal SMTP credentials or signing keys.

## 2. Read-only SQL review — stop if anything differs

In a new SQL Editor query in confirmed quickexit-dev, run each file in full. Both
use `BEGIN READ ONLY`; neither invokes the commit RPC or accesses portfolio payloads.
They return separate JSON results:

1. [v0.8-read-only-security.sql](v0.8-read-only-security.sql).
2. [development-final-verification.sql](development-final-verification.sql).

Compare with the unchanged `supabase/migrations/202610080001_paper_accounts.sql`:

- [ ] Two tables exist: paper_workspaces and paper_operations; RLS enabled **and forced**.
- [ ] Exactly four PERMISSIVE policies, all authenticated only: own-workspace SELECT,
      INSERT and UPDATE; own-operation SELECT. SELECT/UPDATE predicates and write
      checks derive ownership from `auth.uid() = user_id`. No broad OR policy.
- [ ] Effective authenticated table access is SELECT only; anon has none. All direct
      INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER privileges are false for both.
      `column_write_permissions` in the detailed report is null, so no column-level
      grant bypasses table write restrictions. PUBLIC grants inherited by those
      roles must not create additional effective access.
- [ ] Exactly one commit_paper_workspace overload: `(bigint, uuid, jsonb, text)`,
      returns jsonb, PL/pgSQL, default kind save, SECURITY DEFINER and empty search_path.
      The owner is an expected reviewed platform/admin role with superuser or
      BYPASSRLS capability. PUBLIC and anon EXECUTE are false; authenticated is true.
- [ ] Function body matches the reviewed migration. A whitespace-only mismatch
      requires manual comparison, not automatic replacement. Confirm row locking,
      server-derived owner, revision check, owner-scoped UUID replay and one-time import.
- [ ] Workspace columns: user_id, payload, revision, import_decided, updated_at.
      Operation columns: user_id, operation_id, revision, created_at. Types, defaults,
      nullability, PKs, owner auth.users FKs with ON DELETE CASCADE, nonnegative workspace
      revision and version-3/assets/size constraint match the original migration.
- [ ] Constraints and indexes valid; no unexplained application triggers or overloads.
      Migration history includes exact version 202610080001.
- [ ] Record only aggregate row counts and inspecting role visibility. Nonzero counts
      are preserved and investigated; filtered zeros do not prove absence of records.

Missing objects, excessive permissions or unexpected function bodies are stop
conditions. Do not run `development-apply.sql`, migrations, GRANT/REVOKE, ALTER,
TRUNCATE, RESET or repair commands. Review findings before requesting any changes.
SQL Editor's admin identity is not evidence that a real user's JWT is isolated.

## 3. Preparation target — approval required before any change

Request approval specifying the verified development project, the exact settings
that differ, two dedicated email inboxes A/B, the local test origin, and allowed test
writes. Include reversal of any temporary signup window in that approval. No public
production app deployment is needed: a local app can test the hosted development
project. Do not change `.env.local` until its target project and test scope are approved.

Use one origin consistently, preferably `http://127.0.0.1:3000`. The other loopback
hostname is a distinct cookie/PKCE origin; do not switch mid-flow.

| Dashboard area | Development-only target / expected setting |
| --- | --- |
| Authentication / sign-in configuration | Email enabled; Confirm Email enabled; anonymous sign-ins disabled |
| New-user signup | Off normally. A bounded development-only signup test window requires separate explicit approval, followed by restoration to off; never enable production signup |
| URL Configuration / Site URL | `http://127.0.0.1:3000` for this approved local-app test, or the exact separately approved private HTTPS test origin |
| Additional Redirect URLs | Exact `http://127.0.0.1:3000/auth/callback`; add `http://localhost:3000/auth/callback` only if localhost is also an approved origin. No wildcard domains |
| Email templates | Review confirmation and recovery provider verification links. Default `{{ .ConfirmationURL }}` is suitable for provider verification before redirect. Do not replace it with a plain app URL; this app expects a PKCE code at `/auth/callback`, not a custom token_hash flow |
| SMTP | Approved sender and real delivery to both dedicated inboxes. Custom SMTP if recipients are outside built-in service restrictions; never put SMTP credentials in browser env |
| Password policy | At least 12 characters, consistent with app validation; inspect secure-password-change policy and any required reauthentication behavior |
| Sessions | Refresh-token rotation enabled; preserve reviewed security settings. For concurrent-device acceptance, a single-session policy must not invalidate A's second session; report any conflict with policy rather than weakening it without approval |
| Rate limits / email expiry | Keep documented limits and expirations; wait or use newly requested links, never bypass confirmation or disable protections |

The actual callback is `/auth/callback` for **both** signup and recovery. The app
chooses `/app` after verified confirmation and `/reset-password` after a verified
recovery exchange. There is no need to allowlist a direct `/reset-password` email
redirect. Future production origin, if separately approved, is
`https://www.quickexit.net` with exact callback
`https://www.quickexit.net/auth/callback`; do not apply production changes now.

For the approved development-connected local test build, use only the public
project URL and publishable/anon key. Never use service-role or secret keys in the
browser or JWT isolation tests. Enable the local accounts gate only after approval;
keep the normal/public build's accounts and registration flags false. The local
registration flag may be true only during an expressly approved signup test window
against development. A known private test origin is not itself signup authorization.
If temporary signup is not approved, test approved existing dedicated accounts and
mark real signup/confirmation acceptance BLOCKED; admin auto-confirming or inviting
a user is not equivalent to proving this app's signup confirmation flow.

## 4. Build and sessions — approved acceptance work only

- [ ] Use the committed checkpoint and a clean checkout; rerun config validation,
      TypeScript, lint, all tests and production build. Serve the test app locally.
- [ ] GET `/api/build`: commit equals checkpoint, dirty=false, identifier=git-fullSHA,

      to provider commit metadata only after deployment is separately approved.
- [ ] Create independent contexts A1 and A2 for the same test account A, and B1 for B.

- [ ] Use Demo price mode for deterministic trading tests. Capture account-scoped
      baseline revisions and simulated balances only for A/B in private test notes.

## 5. Real confirmation, sign-in, sign-out and recovery

All steps below create or change authentication records, send mail or create/revoke
sessions and therefore belong to approved development acceptance, not read-only review.

1. In A1 sign up A using a unique dedicated inbox and a password of 12–128 characters.
   Expect a confirmation message and no verified workspace until email confirmation.
   Repeat B in B1. Wrong passwords and unknown credentials fail without provider detail.
2. Open the latest real confirmation email in the **requesting browser/context and
   same origin**. Verify `/auth/callback` exchanges a PKCE code, identifies the correct
   user and reaches `/app`. Record only outcome/time; redact callback URLs.
3. Try reused, invalid and genuinely expired links for test accounts. No wrong-user
   session, arbitrary redirect or misleading success. Request a fresh email when needed.
   Do not change expiration settings just to make a test quicker.
4. Close any approved temporary signup window: restore development provider signup off
   and local registration flag false. Existing A/B sign-in must still work. Verify the
   public registration gate remains off. Stop if closing the window cannot be confirmed.
5. Sign in A on A2. Refresh and restart its isolated browser; the same account restores.
   Sign out one context and verify no account data leaks into guest mode. Local-scope
   signout need not terminate another device's session; test the documented behavior.
6. From A1 `/forgot-password`, request a real recovery email. Open the latest link in
   A1, verify provider-confirmed recovery reaches `/reset-password`, matching verified
   identity, and change the password. If the provider requires extra reauthentication,
   record the blocker rather than disabling its protection. No trades or balances change.
7. Verify old password fails and new password succeeds in a separate test login. Invalid,
   expired and reused recovery links fail safely; an unrelated account session cannot
   authorize an update for A. Do not put passwords in screenshots, logs or reports.
8. Check refresh-token expiry/revocation recovery with approved A/B sessions. Mutations
   pause with reauthentication messaging; local data and exact pending operation IDs
   survive. Token-expiry testing must use real provider behavior, not only a browser clock.

## 6. Two-user ownership — use real A/B JWTs, never service-role access

- [ ] A reads only A's workspace/operation rows via Supabase REST under A's JWT.
      B reads only B's. Explicit other-owner filters return zero accessible rows.
      Anonymous requests must not expose records. App `/api/paper` without session is 401.
- [ ] With B's real JWT, attempt direct INSERT/UPDATE/DELETE targeting A's existing
      dedicated-test records; expect permission denial and verify A is unchanged.
      These are approval-required attempts even when denial is expected.
- [ ] Attempt direct writes to B's own tables; they must be denied too. Table policies
      alone do not authorize mutation; only the reviewed RPC has write permission.
- [ ] App POST `/api/paper` containing userId or user_id is 400; cross-origin writes
      are 403. An unauthorized session must not invoke a successful RPC.
- [ ] Direct RPC has no owner argument. Under B's JWT it may only affect B. Try an
      unexpected forged-owner argument and confirm rejection/no change to A.
      Supplying A-like nested payload content does not change the owner: paper data
      are client-authored, and this test concerns ownership rather than anti-cheat.
- [ ] Anonymous RPC and nonexistent/invalid identity fail. Review only dedicated A/B
      state and operation counts; do not enumerate existing users' payloads.

## 7. Demo import and two-device synchronization

1. In A1 guest mode, create a small local demo with a completed trade and note; preserve
   its exact local snapshot privately. Sign in A only if its cloud workspace is empty.
   Review transfer balances, trades, receipts, notes, activity and preferences. Cancel:
   no import write and guest remains unchanged. Confirm once: one cloud decision, no
   merge. Original guest data stays on the device before and after success.
2. In B1 use separate local demo progress; choose Start fresh and confirm. B receives
   €10,000 virtual cash, while its original guest receipts/notes stay on that device.
   On reload neither account offers another import over an initialized cloud portfolio.
3. A1 opens €100 BTC with +€5 net target, Demo prices. Double activation must not create
   a second position, fee or cash debit. Note entry inputs and fixed execution receipt
   assumptions. Refresh, then restore on A2; position, cash and history agree.
4. Close manually or reach the Demo target. Verify exactly one new closed trade and
   receipt. Account cash equals previous cash minus investment plus recorded net
   proceeds; a +€5 target exit is €105 proceeds, **not** the whole account balance.
   Paid fees, realized P&L and portfolio statistics agree with the centralized engine.
5. Add a journal note, refresh A1 and A2: note persists and the immutable receipt does
   not change. Change quotes afterward: closed receipts remain byte-for-byte identical.
   Cloud updates are observed on reload/reconnect/poll; do not claim instant push sync.
6. Offline before a save: pending device data retained and labelled. Reconnect/retry:
   save eventually confirmed. Interrupt after commit but before response using approved
   request interception; refresh/replay same UUID: no extra revision, receipt or cash.
7. With both A devices at revision N, disconnect their sync, create different local
   changes, then reconnect in sequence. One wins; the stale update reports conflict.
   Verify neither portfolio is silently merged or discarded. Cancel leaves both intact.
8. Resolve Use cloud copy: losing device raw is preserved in a recovery key first;
   cash/receipts match the winning record. In a second approved conflict exercise,
   choose Use this device's copy: explicit confirmation, new revision, other device
   observes that choice after restore. If recovery storage fails, resolution must stop.
9. Repeat reauthentication while a command is pending. Account B cannot receive A's
   pending writes; switching/signing out restores the original guest data. Do not use
   Reset Demo or clear browser storage as a generic sync recovery action.
10. Check keyboard focus, errors and 320/390/768/1440px layouts on actual authenticated
    flows. Record exact failures rather than substituting the local fixture results.

## 8. Stop conditions and safe rollback

**Immediately available without hosted mutation:** stop tests, disconnect isolated
contexts, stop the local server, retain local guest/account/recovery snapshots, and
record the last confirmed revision and exact failing step. Do not retry unknown
commands with fresh UUIDs. Do not click a conflict replacement to hide a failure.

**Requires separate approval:** reverse only the documented development settings that
were changed. Keep provider signup closed and rebuild the local test app with both
flags false; never weaken RLS or remove write restrictions. Revoke only dedicated
A/B test sessions if approved. Record that stopping the app does not revoke already
issued JWTs; if authorization exposure is suspected, escalate before resuming tests.

This phase has no schema change, so no migration rollback is needed. Never drop,
truncate, reset or rerun migrations. Do not delete users: auth.users deletion cascades
workspace and operation records. Do not globally roll back cloud payloads, restore a
whole-project backup or change balances to match expectations. Any record repair,
backup restore or cleanup needs an explicit plan/approval and scoped evidence first.
If a future deployment needs rollback, restoring an approved known-good app build
with accounts off is a separately approved deployment; preserve all hosted records.

## 9. Acceptance record and release decision

Record checkpoint SHA, build identifier, project label, UTC date, anonymous labels
A1/A2/B1, each pass/fail/blocked result, revisions/operation counts for test records,
and remaining issues. Never store tokens, passwords or real inbox addresses here.
All security/auth/sync checks must pass before requesting account enablement. Public
registration remains separately gated even after invited-user account acceptance.
A successful local checkpoint is not authorization for rollout.
