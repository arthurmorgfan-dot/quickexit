## Implemented

- Centralized public Supabase configuration validation. Missing configuration keeps accounts disabled and Demo usable; partial/unsafe/privileged-key configuration fails dev/build safely without printing values. Runtime clients fail closed.
- Ignored, empty `.env.local` and isolated `supabase/config.toml` for future local development. No credentials or new dependencies.
- Testable signup/login/logout/session adapters, late-response protection, honest error handling and fixed provider-verified PKCE callbacks.
- Password request/update pages using the existing auth design. Updates use a same-origin, size-bounded, private/no-store server endpoint and verify request-cookie identity against the identity reviewed in the form. Caller-provided email/type/redirect parameters cannot authorize recovery.
- Authenticated paper API extracted into a tested server factory; every request verifies the user and derives ownership from that identity. Unexpected cross-user provider records fail closed.
- Expired authorization shows a sign-in-required status and pauses account mutations. Outages preserve validated device data and pending work. A durable write-ahead journal is required before cloud writes; retries retain operation IDs. Invalid account caches are preserved before restoration, with writes paused if preservation fails. Previous recovery copies are retained; explicit conflict resolution is also blocked if its backup fails.
- Expanded actual-migration PostgreSQL tests for RLS/grants, anonymous JWT subjects, owner-scoped idempotency, hostile search paths and atomic failure.

No visual redesign, financial formula change, new market source or real-money integration. Existing Live/Demo modes, deterministic target controls, immutable receipts, import confirmation and conflict choices remain intact.

## Compatibility and database security

Paper persistence remains **v3**, account journal **v1**. No new SQL migration; the existing migration is unchanged. v1/v2 legacy paper accounting stays distinguishable and is not recalculated. Financial engine and recorded receipt inputs are unchanged. Guest data remains separate from per-user caches; import is explicitly offered only once. Conflicts require a user's copy choice, not silent merging. Invalid account originals are kept in `.invalid` recovery copies (or remain untouched if backup fails); no malformed snapshot is replayed to the cloud.

The database contains one owner-scoped aggregate for positions, cash, receipts and history, plus owner-scoped operation receipts. Forced RLS and restricted grants deny cross-user access/direct mutations; the security-definer write RPC uses `auth.uid()`, an empty search path, row locking, revision comparison and transactional idempotency. This remains a user-controlled paper simulator, not an authoritative real-money ledger. Local caches are not encrypted and are not a security boundary against access to the same browser profile.

## External blockers and acceptance checks

Neither public environment variable is configured. Supabase CLI and Docker are unavailable, so `supabase/config.toml` has not been validated by a running CLI/local stack. No real Auth provider, mail delivery or PostgREST integration has been exercised.

Provide/configure only the authorized non-production project URL and public publishable/anon key in `.env.local`, or install CLI + Docker for the isolated local stack. Never provide a service-role key, database password, exchange/banking credential or production data. [Exact setup instructions](../../README.md#supabase-setup-v041).

Before considering the hosted foundation ready, verify in an explicitly authorized non-production environment:

1. CLI/config compatibility and isolated migration application; real Supabase function ownership, grants/RLS and two actual JWT identities. Remote migration execution still requires approval.
2. Email/password provider, minimum/rate limits, SMTP or local mail capture, confirmation/recovery templates, Site URL and exact callback allowlist.
3. Signup → email confirmation → login → restored session → logout; expired refresh and unavailable Auth behavior. Recovery request → same-browser PKCE link → verified password change → old/new password verification. Provider secure-password-change/session age restrictions must be checked.
4. Actual reverse-proxy HTTPS/cookie handling and private/no-store responses. Callback query parameters and sensitive auth response URLs must not be retained in application/hosting logs.
5. Two real accounts: direct API/RPC reads/writes must never expose the other's aggregate or operations. Test unauthenticated/expired requests.
6. Two browsers/devices: once-only import, restored positions/fixed receipts/history/settings/cash, offline reconnect, lost-response retry and simultaneous revision conflict resolution. Confirm no duplicate proceeds, fees, receipts or transfers.

Hosted integration readiness remains blocked on these external checks. The local checkpoint is validated; v0.5 has not begun.
