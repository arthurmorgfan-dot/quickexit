# QuickExit v0.8 — secure accounts and cloud synchronization

## Local implementation

No migration, trading arithmetic, historical receipt schema or version-3 portfolio
format changed. Existing guest and account data remain compatible. All funds,
executions, fees and transfers stay simulated. No dependencies were added.

### Deployment identity

`GET /api/build` and the workspace footer expose only the app version, full Git SHA,
and a dirty-checkout marker. Next's build identifier uses the same value. The values
are frozen into the build, not taken from a visitor request or runtime secret.
`QUICKEXIT_BUILD_COMMIT` or Vercel's `VERCEL_GIT_COMMIT_SHA` can supply a full SHA;
otherwise a Git checkout supplies HEAD. Invalid metadata or a mismatch with HEAD
fails the build with a generic message. A missing checkout/metadata reports
`unidentified`, never an invented commit. Dirty local builds append `-dirty` and
must not be treated as an exact reproduction of their parent commit.

The v0.8 foundation checkpoint is based on 6a0a0e9. The local release checkpoint is
authorized; a future approved release must be built from a clean checkout and checked through the
public endpoint against its intended commit and deployment provider metadata. A
public SHA is an identifier, not cryptographic deployment attestation. No keys,
URLs, environment dumps, author names, paths or provider configuration are exposed.

### Authentication and registration

Sign-in, sign-out, PKCE email confirmation, password recovery, provider-verified
password changes and session-expiry handling reuse the established Supabase SDK
integration. Public signup now has an independent gate:

- `NEXT_PUBLIC_QUICKEXIT_ACCOUNTS_ENABLED=true` allows account authentication/sync.
- `NEXT_PUBLIC_QUICKEXIT_REGISTRATION_ENABLED=true` additionally permits signup.

Both remain disabled in this candidate's normal environment. Defaults fail closed;
registration additionally requires valid public configuration and enabled accounts.
The auth UI and signup operation enforce the separate gate. Invited-user sign-in
can later be verified without opening public registration. The Supabase provider's
own signup setting must also remain closed; client gates cannot control direct
provider requests. Enabling either gate or changing hosted settings needs approval.

Private provider failures produce generic actionable errors. APIs verify `getUser`
on every protected operation. Account state and pending commands remain segregated
from guest state and other users; expired sessions pause mutations until verified
reauthentication. Recovery/confirmation tests cover invalid links, untrusted
redirects, stale session callbacks and matching identity requirements.

### Database audit

The unchanged migration forces RLS on both tables. Authenticated SELECT policies
use `auth.uid()`. INSERT/UPDATE policies exist on the workspace, but effective direct
write grants are revoked: table/column permissions must be verified together with
policies. Anonymous table access and RPC execution are denied. Authenticated clients
write only through the atomic, owner-derived RPC, with a fixed empty search path.
Its effective hosted owner must be a reviewed platform role capable of the intended
RLS bypass. Workspace owner PK and operation owner/UUID PK scope all records.
Foreign keys reference auth.users. Revision locks, one-time import decisions and
operation UUIDs prevent partial writes, duplicate commits and silent stale overwrites.

Local PGlite tests execute the actual migration. They check A/B isolation, explicit
other-owner filters, denied direct INSERT/UPDATE/DELETE/TRUNCATE, anonymous claims,
owner-scoped duplicate IDs, changed replay payloads, stale revisions, hostile search
paths and nonexistent users. No hosted schema or records were inspected or changed.

The RPC validates aggregate shape; the app validates restored accounting. These are
client-authored paper results, not a server-authoritative financial ledger or trusted
ranking. Never connect this architecture to real funds or prizes.

### Synchronization and opt-in transfer

Reuse account-scoped write-ahead journals, persistent operation IDs, atomic aggregate
commits and revision comparison. Validate cloud acknowledgement identity, payload
and committed revision before clearing retry state. Reject malformed acknowledgements
and preserve pending commands. Old account callbacks cannot change the current user.
Uncertain loads never overwrite remote state. Conflict choices preserve a device
recovery copy before replacement and never merge unrelated portfolios.

The import review shows the captured virtual cash, recorded transfers, selected
asset/price mode, active investment/target/protection/auto-exit settings, completed
trade/receipt/legacy counts, journal count and activity count. It explains that
historical executions, paper preferences and marked examples copy too. Cached
quotes, chart preferences and onboarding state do not transfer. The original guest
key remains untouched, even after successful import. Review and Cancel do not save
an account decision. Confirm is explicit and guarded against repeated clicks.
Starting fresh also requires confirmation when local progress is available.
Only a cloud account confirmed empty can import. If there is no saved demo progress,
the existing flow initializes a clean paper account; it imports no local portfolio.

## Local verification and reproducibility

`npm test` includes actual migration/RLS tests, auth provider fixtures, transport and
store recovery tests, build identity validation, independent registration gates,
acknowledgement validation and captured-transfer tests.

The optional `tests/account-browser.mjs` serves a loopback-only fixture. It renders
the real AccountPanel/DemoImport components and calls real browser transport, HTTP
paper handlers, synchronization stores and the actual migration in PGlite. Auth
identity/session endpoints are explicitly local fixtures, not GoTrue or real email.
No fixture routes or accounts are included in the application build.

Run with an existing external Playwright installation, for example:

```sh
QUICKEXIT_BROWSER_MODULE=/absolute/path/to/playwright/index.mjs node tests/account-browser.mjs
```

At 320, 390, 768 and 1440px it uses A on two independent browser sessions and B on a
third. It verifies reviewed import/cancel, double-click protection, guest retention,
interrupted post-commit responses and refresh replay, matching receipts/journal/cash,
B isolation, forged-owner requests, cross-origin denial, anonymous rejection,
conflict recovery copies, logout isolation and no overflow/runtime errors.

## Hosted verification blockers

Follow the [step-by-step hosted checklist](supabase/v0.8-hosted-verification-checklist.md).
It separates read-only inspection from approved settings/auth/data tests and rollback.

Neither Supabase CLI nor Docker is installed in this environment. Genuine local
GoTrue email/password/refresh-token behavior has not been run. Browser fixture
identities and local RLS results do not prove deployed Supabase JWT isolation,
email delivery, refresh rotation or project configuration. Public accounts remain
closed until separate approval and actual evidence cover these checks:

1. Verify deployed build identity from a clean intended commit and `/api/build`.
2. Perform read-only metadata verification on the confirmed development project;
   compare schema, migration history, RLS, table/column grants, RPC body/owner,
   search_path and execute grants to the unchanged migration. Preserve records.
3. Separately approve development-only dedicated A/B account creation and test writes.
   Confirm origin/redirect allowlists, email confirmation, recovery delivery,
   password change, invalid/expired links and signup policy. Never use customer accounts.
4. Use A in two independent sessions and B in a third with real provider JWTs.
   Verify denied anonymous/direct/cross-owner operations, refresh/logout isolation,
   empty-account opt-in import, two-device restore, duplicate replay, concurrent
   conflicts, interrupted saves, expired/revoked sessions and receipt/note stability.
5. Record results without passwords, tokens, email links or identifying screenshots.
   Do not remove test records or change hosted configuration without approval.

Use [development acceptance](supabase/development-acceptance.md) and the existing
read-only `development-final-verification.sql`. Do not rerun migrations casually.
This phase completes local work only; no hosted verification is claimed.
