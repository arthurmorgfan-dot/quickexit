2. Open a **new, empty** SQL Editor query. Copy the entire SQL file, including its

3. Run only this query. Do not include earlier editor text, migration SQL,

## Interpretation

All eight `checks` should be PASS:

- `required_tables_and_rls`: both expected account tables exist, with enabled and
  forced RLS; every detected public account-owned table also has both flags.
- `unexpected_account_owned_tables`: no additional public table has `user_id` or
  an FK to auth.users. REVIEW requires identifying its purpose, policies and
  grants separately. This inventory is a heuristic, not proof that ownership
  hidden behind other column names, views or other schemas does not exist.
- `client_roles_cannot_bypass_rls_or_assume_table_owner`: anon/authenticated exist,
  cannot bypass RLS, are not superusers and cannot assume an inventoried owner.
- `exact_ownership_policies`: exactly the migration's four authenticated-only
  ownership policies, including both UPDATE predicates and checks. The report
  compares full expressions, not a substring that could hide a broad OR condition.
- `effective_table_and_column_grants`: authenticated SELECT only, anon no table
  access, neither role has direct writes or column write/reference privileges.
- `columns_constraints_indexes_match_migration`: exact ordered columns, types,
  nullability, defaults, named PK/FK/check constraints and valid indexes match the
  reviewed migration. PostgreSQL-version-specific NOT NULL catalog constraints
  are excluded; column nullability remains checked. Cosmetic catalog formatting
  differences can produce FAIL and must be manually reviewed.
- `no_unexpected_triggers`: no noninternal triggers on the account tables.
- `commit_function_security_and_body`: exactly one expected overload; jsonb return,
  PL/pgSQL, default 'save', SECURITY DEFINER, only an empty search_path setting,
  owner postgres with superuser/BYPASSRLS capability, authenticated EXECUTE only,
  and the exact reviewed function body. A different owner or whitespace-only body
  difference still fails until reviewed; never automatically replace it.

`migration_history` contains only version/name metadata as XML. Confirm version
`202610080001` corresponds to `paper_accounts`. MISSING, an absent version, or
unexpected entries require review. SQL Editor application may not register history;
that is a traceability discrepancy, not permission to reapply the migration.
Matching schema/body and history cannot prove the original migration file bytes.

`other_public_security_definer_functions` should be null for a project containing
only this reviewed application function. Any entries require a separate audit of
purpose, owner, identity derivation, search_path and execution grants; no automatic
PASS is assigned to them. Platform functions may be legitimate, but an unexpected
privileged API must not be ignored.

Any FAIL, REVIEW, missing metadata, permission error or SQL error is a stop condition.
Capture the nonsensitive error/check name and compare the metadata against
`supabase/migrations/202610080001_paper_accounts.sql`. Do not change RLS, grants,
functions, tables, migrations or hosted records to make the report pass.

Local validation used the actual migration in an isolated PGlite database. All
checks passed; an excessive INSERT grant and a broad ownership policy each caused
its corresponding check to fail. The hosted migration-history XML branch uses
PostgreSQL's catalog SELECT helper and remains to be verified in Supabase.
Metadata verification under the SQL Editor's administrator role does not prove
real JWT ownership isolation or synchronization. Those remain approval-required.
